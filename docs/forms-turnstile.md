# Form submission and Turnstile

## Current behavior

The contact, compact demo, and full demo forms use native `POST` submissions. Newsletter forms use the shared `SubscribeField`, whose action can be overridden by a component prop. Without Turnstile configuration, the default forms use a `#` action and do not load Turnstile. A valid submission to this unconfigured action is stopped in the browser and shows a localized error message; it is not sent.

Once an endpoint is configured, submissions remain native `POST` requests. Failures returned by that endpoint are not intercepted by the site; the endpoint must provide its own error response or redirect behavior.

There is currently no form-processing endpoint in this Astro project. The forms must not be considered protected until a real server endpoint is deployed and configured to verify tokens. While that endpoint is unavailable, a blank white verification-field preview is shown for layout work. It is design-only and does not submit a token. Set `formsVerificationPreviewEnabled` to `false` in `src/config/forms.ts` to hide the preview while retaining its component styling.

## Enable after deploying an endpoint

Configure these **build-time frontend** variables only after the endpoint below is live:

| Variable | Purpose |
| --- | --- |
| `PUBLIC_FORMS_ENDPOINT` | The HTTPS URL that receives all form submissions. |
| `PUBLIC_TURNSTILE_SITE_KEY` | Cloudflare Turnstile site key for the website's allowed hostnames. This key is public. |

The widget, endpoint action, and Cloudflare API script are enabled only when both variables are non-empty. Otherwise the original `#` actions remain in use. Rebuild/redeploy the static site after changing either variable.

Set the Turnstile **secret key** as a server-side secret on the endpoint's hosting platform (for example, `TURNSTILE_SECRET_KEY`). Never use a `PUBLIC_` prefix for it, place it in Astro client code, or include it in the generated website.

## Endpoint contract

Implement and deploy the endpoint before setting the frontend variables. It must:

1. Accept HTTPS `POST` requests and handle the submission form fields. All forms share the configured URL; the `formType` field identifies `newsletter`, `contact`, `demo-compact`, or `demo-full`.
2. Read the `cf-turnstile-response` field generated by the Turnstile widget. Reject missing or invalid tokens before storing, forwarding, emailing, or otherwise processing a submission.
3. From the server, send the token and server-only secret to Cloudflare Siteverify at `https://challenges.cloudflare.com/turnstile/v0/siteverify`. Enforce a successful response and, where applicable, check that the returned hostname matches an allowed site hostname. Treat network errors, malformed replies, and verification errors as failures; do not process the submitted form on failure. Tokens are single-use and short-lived, so do not cache or reuse them.
4. Validate and safely process the other submitted values independently of Turnstile. Apply request-size limits, spam/rate limits, and an explicit policy for allowed origins as appropriate to the deployment.
5. Handle the demo and contact forms as `multipart/form-data` once enabled; these forms include file inputs. Enforce file type and size limits server-side. Newsletter forms submit the same endpoint as regular URL-encoded form data.
6. Return an appropriate success or error response, and configure the endpoint's CORS/redirect behavior as needed for the website's deployment.

The browser widget only obtains a token; it is not verification. A configured endpoint that does not perform server-side Siteverify validation does not provide Turnstile protection.
