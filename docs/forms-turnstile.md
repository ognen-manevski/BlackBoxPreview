# Form submission and Turnstile

## Current behavior

The contact, compact demo, full demo, and newsletter forms use the shared submission-feedback flow. While a request is pending, the submit button shows a spinner and is disabled. A per-form cooldown also limits rapid repeat submissions in the browser.

Each form includes a visually hidden `jobTitle` field as a low-cost spam signal. The browser does not send the request if it is filled, but clients can bypass JavaScript and submit directly. The full demo form also has a separate, optional `website` field for the company's website.

Without Turnstile configuration, the default forms use a `#` action and do not load Turnstile. A valid submission is not sent; after the loading indicator, the form shows a localized error message.

Once an endpoint is configured, the browser submits with `fetch` so it can show feedback without leaving the page. A response is considered successful only when it has a 2xx status and a JSON body containing `"success": true`. On success, the form is reset and a localized confirmation is shown. Network errors, non-2xx responses, invalid JSON, or any other response shape show the localized error and preserve the entered values.

There is currently no form-processing endpoint in this Astro project. The forms must not be considered protected until a real server endpoint is deployed and configured to verify tokens. While that endpoint is unavailable, a blank white verification-field preview is shown for layout work. It is design-only and does not submit a token. Set `formsVerificationPreviewEnabled` to `false` in `src/config/forms.ts` to hide the preview while retaining its component styling.

## Enable after deploying an endpoint

Configure these **build-time frontend** variables only after the endpoint below is live:

| Variable | Purpose |
| --- | --- |
| `PUBLIC_FORMS_ENDPOINT` | The HTTPS URL that receives all form submissions. |
| `PUBLIC_TURNSTILE_SITE_KEY` | Cloudflare Turnstile site key for the website's allowed hostnames. This key is public. |

The widget, endpoint action, and Cloudflare API script are enabled only when both variables are non-empty. Otherwise the original `#` actions remain in use. Rebuild/redeploy the static site after changing either variable.

Set the Turnstile **secret key** as a server-side secret on the endpoint's hosting platform (for example, `TURNSTILE_SECRET_KEY`). Never use a `PUBLIC_` prefix for it, place it in Astro client code, or include it in the generated website.

## Endpoint contract

Implement and deploy the endpoint before setting the frontend variables. It must:

1. Accept HTTPS `POST` requests and handle the submission form fields. All forms share the configured URL; the `formType` field identifies `newsletter`, `contact`, `demo-compact`, or `demo-full`. The `website` field is an optional URL on `demo-full` only.
2. Read the `cf-turnstile-response` field generated by the Turnstile widget. Reject missing or invalid tokens before storing, forwarding, emailing, or otherwise processing a submission.
3. From the server, send the token and server-only secret to Cloudflare Siteverify at `https://challenges.cloudflare.com/turnstile/v0/siteverify`. Enforce a successful response and, where applicable, check that the returned hostname matches an allowed site hostname. Treat network errors, malformed replies, and verification errors as failures; do not process the submitted form on failure. Tokens are single-use and short-lived, so do not cache or reuse them.
4. Reject any non-empty `jobTitle` value. Treat it and the browser cooldown as signals, not substitutes for server-side protection.
5. Validate and safely process every field independently of Turnstile. Allowlist `formType`, enforce type and length limits, and reject unexpected fields and content types.
6. Apply edge and endpoint rate limits (for example, by trusted client IP and normalized email), plus request and multipart body-size limits. Use strict deployed-origin CORS; CORS does not prevent direct requests.
7. For contact/demo attachments, enforce an explicit file count, size, extension, MIME type, and file-signature policy. Scan uploads and store them under generated names outside executable/public paths.
8. Add email verification or double opt-in for newsletters, deduplicate submissions where appropriate, and return generic errors. Keep logs free of unnecessary personal data and never expose server details.
9. Return a 2xx JSON response containing `{"success": true}` only after the submission has been accepted. Return a non-2xx response or a JSON body without that confirmation for failures. If the endpoint is cross-origin, configure CORS to allow the deployed website.

The browser widget only obtains a token; it is not verification. A configured endpoint that does not perform server-side Siteverify validation does not provide Turnstile protection.
